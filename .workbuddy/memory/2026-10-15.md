## 排查 `:id` 路径参数：string 传入 vs number 定义（结论：不失败，但有个边界漏洞）

- `idParamSchema = z.coerce.number().int().positive()`（在 `reset-password.dto.ts`）——用了 **coerce**，所以 `'12'` → `12`；若写成裸 `z.number()` 则所有 `:id` 路由都会 400
- 实测（项目内 zod 4.6.7）：`'1e0'→1`、`'+1'→1`、`'0x10'→16`、`' 12 '→12`（Number() 吞空白）、`'2.0'→2`、`'1.'→1` 全部通过；`'0'`/`'-1'`/`''`/`'  '` → 400（positive 失败，path 为空串）；`'1.5'` → 400（int）；`'abc'`/`'Infinity'`/`'NaN'`/`'1_000'` → 400
- zod v4 的 `.int()` 实际按**安全整数**校验（>9007199254740991 报 Too big），所以超大数不会走到 DB
- **int4 边界（用户决定不处理）**：users.id 是 `integer()`（PG int4，上限 2147483647），而 zod 只到安全整数。实测 `id = 2147483648` 通过校验后到 PG 报 `22003 out of range for type integer`，`handlePgError` 只处理 23505 → 冒泡成 500。用户明确说 id 由 DB 生成、不可修改，**不需要处理**（本节后半段记录了问题 1/2 的修复）
- `idParamSchema` 原先在 `user-dto.spec.ts` 中无测试用例 → 已补（见下节）
- 验证方式说明：本机 8000 端口无监听（开发服务器未运行，未按约定自行重启），故用项目内 zod/ pg 直连 DB 实测而非 curl

## 首尾空白 trim（社区调研 → 落地 → 重构为 shape 级包装）

- **决策**：全部文本字段 trim；trim 后为空 → 视为「未提供」（衔接空串/null 约定）；不压缩内部空白、不处理零宽字符（已知缺口：U+200B 能通过 min(1)）
- **落地（第一版）**：新建 `src/common/validation/trimmed.ts`，用 `z.preprocess` 包装——trim 后为空返回 `undefined`，从而得到内建的「received undefined」必填缺失语义（`z.string().trim()` 只能报 too_small，`overwrite()` 不能返回 undefined）
- **重构（第二版，用户问"每个 schema 都要加？"）**：新增 `trimmedShape()`，DTO 写法变为 `z.object(trimmedShape({...}))` / `paginationSchema.extend(trimmedShape({...}))`，每个 DTO 一行
  - 实测依据：`schema.shape` 可遍历；`.meta()`/`globalRegistry` 可用；只重建 shape 不重建对象 → `.refine()`/`.strict()` 不丢
  - 语义与第一版**完全等价**（重构后原有 24 项 DTO 测试未改仍全绿）
- **顺带修复的两处既存缺陷**：① `updateUserSchema` 的 refine 用 `Object.keys` 判定过弱（`{nickname: undefined}` 会误判为"提供了字段"→ 200 静默 no-op），改为 `Object.values(v).some(x => x !== undefined)`，现在只传空值 → 400「至少提供一个更新字段」；② `GET /users/by-student-no/:studentNo` 原本没有任何校验管道，超 20 字符学号触发 PG `22001` 冒泡为 **500**，加 `studentNoParamSchema = trimmed(studentNoSchema)` 后变 400
- **测试**：`trimmed.spec.ts`(18) + `user-dto.spec.ts`(25) + `zod-validation.pipe.spec.ts`(11) + `log-levels.spec.ts`(4) = 58 项全绿；测试陷阱：zod v4 保留值为 undefined 的键而 `JSON.stringify` 会隐藏，断言必须用 `Object.values`/属性断言
- **端到端**：25 项 HTTP + DB 断言全部通过（带空白学号/邮箱/昵称入库已规范化、纯空白必填 400「received undefined」、keyword 空白不筛选、枚举大小写敏感、by-student-no 带空格 200 / 超长 400、库中 password_hash 为 scrypt 非明文）；验证数据已清理
- **启动方式教训**：本环境 `run_in_background` 启动的应用从不 listen（进程在、无任何输出）；改用前台脚本 `spawn('node',['dist/main.js'])` + fetch 断言 + kill 才成功

## 修复 `:id` 路径参数（用户要求：解决问题 1、2；int4 上限明确不处理）

- **问题 1**：`idParamSchema` 原为 `z.coerce.number().int().positive()`——管道层"空串归一化"不覆盖顶层字符串，`Number('') === 0` 导致空/纯空白被误报成 `Too small: expected number to be >0`；且 `Number()` 解析过宽松（`'0x10'`→16、`'1e0'`→1、`'+1'`/`'1.'` 照收）
  - 改为 `trimmed(z.string().regex(/^\d+$/, { error: 'ID 必须是正整数' }).transform(Number).pipe(z.number().int().positive()))`
  - 空白值 → 「未提供」→ `expected string, received undefined`（与其他参数缺失语义一致）；非纯数字统一 `ID 必须是正整数`；`'0'`/`'000'` 仍 `>0`；20 位以上数字串 `Too big`（`.int()` 按安全整数）
  - 用户明确表态：**id 不可修改且只能数据库生成，int4 上限（2147483648 → PG 22003 → 500）不需要处理**
- **问题 2**：`user-dto.spec.ts` 补 `describe('idParamSchema：:id 路径参数')` 7 个用例（含经管道后的契约形态、管道层不处理顶层字符串）→ `pnpm test` 72 passed
- 端到端 curl 验证 15 项：`/users/abc|%20|0|0x10|1e0|+1|1.5|12abc|99999999999999999999` 全 400（errors 形态正确）；创建临时用户后 `/users/14`、`/users/%2014%20`、`/users/0014` 全 200；`abc/password`、`1e0/restore`、`0x2` DELETE 全 400；验证后测试用户已硬删除（users 表恢复 0 行）
- AGENTS.md §6 同步新增"路径参数两个方向都要显式处理"的规则（文本类 trimmed / 数字类 regex+transform），并说明数字 ID 由 DB 生成故不约束业务范围

## 用 drizzle 自定义迁移灌 10 万条拟真用户数据

- 走完整 drizzle 迁移流程：`pnpm db:generate --custom --name=seed_users` → 生成 `drizzle/0001_seed_users.sql`（空文件）+ 自动更新 `meta/_journal.json` 与 `0001_snapshot.json` → 手写 SQL → `pnpm db:migrate` 应用（6.5s）
  - 确认此前 0000 已由 `drizzle-kit migrate` 应用（`drizzle.__drizzle_migrations` 有记录），DB 走的是 migrate 流程而非 push
  - `--> statement-breakpoint` 在 psql 里也是合法注释，因此**同一份迁移文件可用 psql 在 `BEGIN ... ROLLBACK` 里试跑验证**，不污染数据
- 数据生成技巧（单条 `INSERT ... SELECT generate_series` + CTE 分层，因 PG **不能在同一个 SELECT 列表里引用输出别名**，故按 raw→dims→stamped→shaped 四层 CTE 逐层加列）：
  - `SELECT setseed(0.20261015)` 固定种子让分布可复现（migrate 按 breakpoint 在**同一连接**执行，setseed 对后续语句生效）
  - 学号 = 入学年(4)+院系(2)+届内序号(4)，100 个"届"（13 院系 × 8 年）× 1000 人；created_at = `make_timestamptz(入学年, 8, 20)` + 45 天抖动（落在真实入学季且不晚于 now）
  - 姓名/邮箱用**中文与拼音并行数组**按同一随机下标取值，保证中文名与拼音邮箱一致
  - 密码哈希用 **scrypt 存储格式的合成串**（`md5(random()::text)` 拼盐 32hex + 64 字节 128hex），无法在 SQL 里算真 scrypt；另把前 3 条写成**真实 scrypt 哈希（密码 12345678，学号 2019010001~3）**，已用 node 按项目 verifyPassword 逻辑验过能通过
  - `ON CONFLICT (student_no) DO NOTHING` 保证幂等
- 校验结果：100000 行、学号唯一、软删除 3487(3.49%)、管理员 3037(3.04%)、平均积分 4268、哈希/时间不变量异常数均为 0；接口侧 `total=96513`（= 10 万 − 软删除），keyword/role/深分页/by-student-no 全部正常
- ⚠️ 坑：**identity 序列不参与回滚**。两次事务内试跑 + 一次正式 migrate 共消耗 30 万个序列值，导致 id 实际从 200017 起（200017~300016）。已确认 `users_id_seq.last_value = max(id)`，后续新记录 id 连续无缺口；若要 id 从 1 开始需 `TRUNCATE users RESTART IDENTITY` + 删 `drizzle.__drizzle_migrations` 中 0001 记录 + 重跑 migrate
