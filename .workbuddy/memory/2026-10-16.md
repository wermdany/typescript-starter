## 启动检测：打印服务地址 + 分段耗时

**用户需求**：「编写项目启动时检测，检测时长，并且打印日志具体的服务地址」

**已定取舍**：① 地址范围 = 回环 + 局域网 IPv4（不打 IPv6 回环），单独说明监听地址；
② 检测范围 = 分段耗时 + 总计（不做启动自检）；③ **不加 HOST 变量**，维持 `listen(port)` 通配监听。

**关键发现（决定了方案形状）**：
- **`app.getUrl()` 在本项目返回 `http://[::1]:8000`**，不是 `127.0.0.1`：`listen(env.PORT)` 未传 host →
  macOS 绑 IPv6 通配 `::`（`lsof` 实测 IPv6 `*:8000`），而 `@nestjs/core` 的 `formatAddress`
  （`nest-application.js:336-357`）只把 `0.0.0.0`→`127.0.0.1`、把 `::`→`[::1]`。
  **所以地址不能靠 `getUrl()`**，只借它取协议前缀。
- `NestFactory.create()` **不调用** `instance.init()`（`nest-factory.js:102-108`），`init()` 幂等
  （`nest-application.js:112-115`），`listen()` 会跳过已初始化的实例（`:291-295`）；
  `registerParserMiddleware()`（`:126`）与 `callInitHook()`（`:129`，即 `OnModuleInit`）都在 `init()` 内；
  `app.use()` 是**即时转发**（`:251-254`）。
  → 因此可以**显式 `await app.init()`** 把「模块初始化（含 DB `SELECT 1`）」与「端口绑定」拆开计时，
  且只要 `app.use(traceContextMiddleware)` 仍在 `init()` 之前，中间件顺序保证不破。

**改动**：

  `interfaces` 可注入以便单测）与 `describeBoundAddress(address)`（`null`→尚未监听、
  `::`→`[::]:8000（所有网卡 · IPv6 通配）`、`0.0.0.0`→`0.0.0.0:8000（所有网卡）`、unix socket 原样）

## 失败日志三条 → 一条：access 日志下沉到中间件层（社区对齐）

**用户提问**：「当失败时，打印了三条日志，为啥？参照社区方案应该如何优化」

**三条的来源**：① 拦截器入口的 body 行（LOG_BODY）② 拦截器 error 分支的 access 行
③ 过滤器的 4xx 行。**②③ 语义重叠**（同一个 400、同一句「参数校验失败」）。

**社区结论（查证后引用）**：
- "a filter and an interceptor will both see the same exception… registering capture in both means
  every HTTP failure is reported twice. **Pick the filter. Interceptors are for shaping responses and
  timing, not for reporting.**" + "**4xx is the client's problem. Reporting it burns budget and buries
  real bugs.**"（docs.infrai.cc，NestJS error tracking）
- `pino-http` 默认行为：**一个请求恰好一行**（req + res + responseTime 同条），
  `customLogLevel` 4xx→warn / 5xx→error，失败原因拼进同一行，**不为 4xx 另记一条**

**已定取舍**（用户选）：① access 日志**完全下沉到中间件层**（morgan/pino-http 同位置，每请求恒定 1 行）
② body 行保留独立行（挂死/中断时仍看得到请求体）③ 5xx 的 access 行保留简短原因

**实测结论（方案地基）**：用内存 express 服务测三种收尾路径 ——
正常 `res.json`、`res.status(400).json` 的 `finish`/`close` 回调里 `storage.getStore()` **有值**；
**客户端提前断开只有 `close` 触发，且 `getStore()` 为 `undefined`**（socket 触发，不在请求 ALS 上下文内）。
→ 因此**必须**：入口 `const traceId = getTraceId()` 捕获 + 写日志时 `runWithTraceId(traceId, …)` 恢复 +
`finish`/`close` 双监听单次守卫（只监听 finish 会让中断请求零 access 行，是**回归**）。

**改动**：
- 新增 `src/logger/access-log.middleware.ts`：`accessLogMiddleware`（唯一 access 行出口）+
  `formatFailureSuffix()`（纯函数，含 `toSingleLine` 压平与「最多 3 字段」裁剪）+ `FAILURE_LOCALS_KEY`
  + `AccessLogFailure` 类型；级别 ≥500 error / ≥400 warn / 其余 log，**中断一律 warn**
- `HttpExceptionFilter`：**只记 5xx**（带堆栈）；4xx 不再记；两类都把结构化摘要写
  `res.locals.accessLogFailure = { summary, fields? }`（`fields` 给完整列表，裁剪归日志层）
- `RequestLoggingInterceptor`：删掉 `tap()` 与全部 access/失败逻辑，只剩 body 行
- `main.ts`：`app.use(accessLogMiddleware)` 紧跟 trace 中间件之后（顺序不可换）
- 新增 2 个 spec + 重写 1 个：`access-log.middleware.spec.ts`（11）、
  `http-exception.filter.spec.ts`（6，此前无 spec）、`request-logging.interceptor.spec.ts`（3）

**踩到的坑**：spec 里最初用 ConsoleLogger 断言，ConsoleLogger 给**级别与 context 分别上色**，
转义码夹在 `LOG` 与 `[HTTP]` 之间导致 `toContain('LOG [HTTP] …')` 失败；写清理正则又触发 oxlint
`no-control-regex`。→ 改用 **FileLogger + 读落盘文件**断言（它本就剥 ANSI、且带 `[traceId=…]`），
顺带让「ALS 上下文恢复」这个用例变得可测（ConsoleLogger 根本不看 traceId）。

**live 验证**（watch 自动重编译，未重启服务）：200 / 400 / 404 / malformed JSON / 409 / 5xx /
入站透传 全部符合预期 —— 400 与 409 各 1 行 access（不再有过滤器行，`grep` 确认改后 4xx 过滤器行为 0）；
404 与 malformed 400 各 1 行且**带耗时**（1ms / 2ms）；
5xx 恰好 2 行（堆栈行在前，`--enable-source-maps` 让堆栈显示 `user.controller.ts:78:11`）；

## 入参归一化收窄到 query：制定「body 必须干净」的前端契约

**用户需求**：「清空现在空串，null 过滤等信息，制定契约，必须由前端处理。如果参数在 url query 则做处理」
（追问后用户定调：① body 内**仅处理前后空格**；② query 落点"结合社区分析那个更好"）

**社区查证（两条地基）**：
- **query 是传输层假象**：URL 的值永远是字符串装配产物，浏览器表单 / `URLSearchParams` 无法表达
  "键不存在"（清空输入框天生就是 `?keyword=`）。Nest 社区对 query 的标准答案就是"在管道里 transform"
  （`ArgumentMetadata` 正是为此设计）。
- **body 的 null/`""` 是显式语义**：RFC 7396（JSON Merge Patch）与 Quinyx / MCPProxy 等生产 API 规约一致 ——
  `null` = 删除该字段、`""` = 长度为 0 的真实值，**只有"键缺席"才是"没有值"**。
  "Treat null as an explicit delete, and never as a default for 'no value available'."
  → 把 null 吞成"未提供"会让 PATCH 无法表达"清空某字段"。

**落点选择**：管道内按 `metadata.type === 'query'` 自动分流（而非调用点显式声明 `{ source: 'query' }`、
也不是独立中间件）。理由：调用点零改动、`@Body/@Param` 自动严格、新增路由不会漏写标记；
中间件方案需改写 Express 的 `req.query` 且对无 query 管道的路由也生效，脱离"管道=唯一校验入口"的分层。

**改动**：
- `src/common/pipes/zod-validation.pipe.ts`：`transform(value, metadata?)` 读来源；`emptyishToUndefined`
  → `normalizeQueryValue`（只在 query 生效，顺带把**纯空白**也归零，此前 `?page=%20%20` 会被
  `Number('  ')==0` 误报 `too_small`）；不传 metadata 时走严格分支
- `src/common/validation/trimmed.ts`：`trimmed` **只 trim、不产出 undefined**（`preprocess` 保留，
  因为要无差别包裹非字符串字段）；文档里写明"空值语义不属于 schema 层"
- 4 个 DTO 注释同步（create/update/query/reset-password）+ AGENTS.md §2/§6/§12/§13
  （§6 整节重写为「请求校验与前端契约」，含 body 契约表格与 RFC 7396 依据）
- 3 个 spec 重写：`zod-validation.pipe.spec.ts`（22）、`trimmed.spec.ts`（21）、`user-dto.spec.ts`（44），
  新增 query vs body 双向覆盖

**行为变化（对外可见，前端需要知道）**：
- body 传 `""` ≥ 400 `Too small: … >=1`（原来被当成"未提供"）；body 传 `null` → 400 `received null`
  （原来被吞掉，PATCH 尤其危险）
- body 枚举字段传 `""` → 400 非法枚举（原来静默回落 default）
- update 类 DTO 传 `{"nickname":""}` → 字段级 400（原来落到 refine「至少提供一个更新字段」）
- query 侧完全保持原行为（`?page=&pageSize=&keyword=`／纯空白都当未提供）
- 路径参数 `:id` 空白 → 「ID 必须是正整数」（原来是 `received undefined`）

**验证**：`tsc -p tsconfig.build.json` exit 0、`pnpm lint` 0 error（1 个既有 warning）、
`pnpm test` **181 passed / 14 files**；live curl 14 项 —— query 空串/纯空白均 200 走默认值、
body 空串/纯空白/`null` 分别 400 且 `errors[].path` 指向字段、`:id` 非数字与空白报「ID 必须是正整数」、
PATCH `{}` 走 refine、404/409/`pageSize=200` 正常；日志侧 4xx 仍是**稳定 1 行** access warn + traceId 前置，
无重复。全部用例都在校验或 409 处被拦，**未产生任何测试数据**。

## 响应契约重构：`{code,message,data}` → `{success,message,data}`

**用户需求**：「研究改进请求成功响应契约，首先得知目前契约，再参照社区优秀方案，给我选择」

**研究结论（社区）**：
- **成功响应不该套信封**——"Wrapping makes sense when you need to co-locate metadata that isn't part
  of the resource itself — pagination cursors, request IDs... Don't make clients write `response.data.order.id`
  when `response.id` works just fine."（jsonparser.ai；vikulin-va 直接称 envelope 为 antipattern）。
  Google AIP / Stripe / GitHub 的单资源响应都是裸资源。
- **错误应该用 RFC 9457 Problem Details**（2023 取代 RFC 7807）：`application/problem+json` 五字段
  `type/title/status/detail/instance`，字段级校验作扩展成员 `errors[]`；两条硬规则：`status` 必须与真实
  HTTP 状态一致；**绝不用 HTTP 状态码当业务错误码**（"`{"code": 402}` adds nothing the status line
  did not already say"）。
- 信封只在"混合载荷"（列表 + 分页元数据、批量部分成功）处合理。

**诊断出的 5 个问题**：① `code` 一个字段两种尺度（成功哨兵 0 / 失败 HTTP 状态）② `code` 与 HTTP 状态
完全冗余 ③ `message:'ok'` 纯噪声 ④ `@ApiMessage('创建成功')` 把不可 i18n 的 UI 文案塞进契约，
客户端只能字符串匹配 ⑤ `void` 接口回 200+`data:null`；`totalPages` 可推导、`total` 每页跑 `COUNT(*)`。

**给了三个候选方案**（A 收敛信封 / B 裸资源+RFC 9457 / C 轻信封 data+meta，附对比图），
**用户拍板**：不要 code，用 `success` 当唯一成功判据，`message` 直接作 toast 文案；
追问后确认 message **恒有值默认 `ok`**、校验失败文案**要留自定义入口**、分页**保持现状不动**。

**改动**：
- `src/common/response/api-response.ts` 重写：`ApiSuccess<T>` / `ApiFailure` / `ApiResponse<T>` 判别联合
  + `DEFAULT_SUCCESS_MESSAGE` / `DEFAULT_VALIDATION_MESSAGE` 两个常量
- `transform.interceptor.ts` 输出 `success:true`；`http-exception.filter.ts` 输出 `success:false`（去掉 `code`）
- `zod-validation.pipe.ts` 加 `ZodValidationPipeOptions.message`（默认取 `DEFAULT_VALIDATION_MESSAGE`）
- `api-message.decorator.ts` 文档写明"该文案会直接展示给用户"
- AGENTS.md §2/§5/§12/§13：§5 整节重写，新增「两条硬性不变量」与「为什么没有 code（不要加回来）」
- 单测：`http-exception.filter.spec.ts` 6→9（含 success 不变量、无 code 断言）、
  `zod-validation.pipe.spec.ts` 22→25（含自定义文案）

**推导出的连带结论（已写进 AGENTS.md，避免后人踩）**：
- **不改 204**：`PATCH /:id/password` 这类无返回值接口必须保持 `200 + {success:true,data:null}` ——
  判据在 body 里，204 无 body 会断掉前端唯一判据
- **`success === (2xx)` 是硬不变量**，绝不允许 200 + `success:false`
- **`message` 从此不是机器判据**：客户端只能靠 `success`/HTTP 状态码/`errors[].path` 分支；
  代价是服务端只有中文、不 i18n（多语言由前端映射），好处是改文案不再算契约变更

**验证**：`tsc -p tsconfig.build.json` exit 0、`pnpm lint` 0 error（1 个既有 warning）、
`pnpm test` **187 passed / 14 files**；live curl 8 项 —— 列表 `{"success":true,"message":"ok",...}`、
创建 201 +「创建成功」、400 带 `errors[]`、404/409 `success:false`、
reset-password 回 `{"success":true,"message":"密码已重置","data":null}`、
`grep -c '"code"'` 为 **0**（无遗留字段）。测试用的 T9000002/T9000003 两条记录已用 psql
**物理删除**（`SELECT count(*) ... LIKE 'T90000%'` = 0）。
