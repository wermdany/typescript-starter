# CI 与测试策略

> 回答一个问题：**哪条验证在本地跑、哪条只在 CI 跑、为什么这么切。**
> 改 `.github/workflows/ci.yml`、`package.json` 的 scripts、或决定"要不要跑测试"之前读这一份。

---

## 1. 一条分工原则

| 问题 | 谁回答 | 成本 |
| --- | --- | --- |
| 这次改动成立吗？ | 本地：`pnpm verify` + 目标 `curl` | 秒级 |
| 这次改动碰坏别的东西了吗？ | CI：构建 + 全部单测 + e2e + 迁移 | 分钟级 |

两件事不是一回事。本地那几十秒的检查能回答"语法、类型、规范、这条路由的响应对不对"，
回答不了"365 个用例是否仍然成立"，而后者恰恰是**回归**的定义 —— 回归只会在合并前后暴露，
所以在本地刷它只是在用时间换一个"我跑过了"的心理安慰。

结论：**日常开发不跑单元测试、不跑 e2e、不跑构建**；这三件事固定在 CI。

---

## 2. 命令分工

| 命令 | 本地日常 | CI | 说明 |
| --- | --- | --- | --- |
| `pnpm typecheck` | ✅ | ✅ | `tsc --noEmit`，零副作用 |
| `pnpm lint` | ✅ | ✅ | oxlint + `convention-audit`（20 条规范规则） |
| `pnpm perm:audit` | ✅ | ✅ | 路由访问意图标注，纯 AST 不连库 |
| `pnpm verify` | ✅ | ✅ | 上面三条串起来的日常入口 |
| 目标 `curl`（400/404/409） | ✅ 动接口时 | ❌ | CI 里没有运行中的应用，靠 e2e 覆盖 |
| `pnpm build` | ❌ | ✅ | 会动 `dist/`、可能干扰 watch 进程 |
| `pnpm test` | ❌ | ✅ | 单元测试（31 个文件 / 365 个用例，本机约 3 分钟） |
| `pnpm test:e2e` | ❌ | ✅ | 需真实库；当前无用例，CI 里 `--passWithNoTests` |
| `pnpm db:migrate` | 按需 | ✅ | CI 在干净库上跑一遍，验证 `drizzle/` 的 SQL 可执行 |
| `pnpm ignored-builds` | ✅ 加依赖后 | ❌ | 只读诊断：有没有没裁决的安装脚本，见 §5 |
| `pnpm test:watch` / `test:debug` | ✅ 改测试本身时 | ❌ | 交互式工具，不受守卫限制 |

发版另加：`pnpm build` + `pnpm test` 在 CI 里已经跑过，不需要再手动重复。

## 3. 守卫：本地误跑测试会被拦住

`scripts/test-guard.mjs` 挂在 `pretest` / `pretest:cov` / `pretest:e2e` 上（pnpm 会自动执行
`pre<script>` 钩子），不在 CI 环境运行时直接以退出码 2 中止，并打印替代方案。

```bash
pnpm test                 # 本地 → 被拦截，退出码 2
TEST_ALLOW_LOCAL=1 pnpm test   # 显式覆盖 → 正常执行
```

放行条件只有两个：`CI=true`（GitHub Actions 自带），或 `TEST_ALLOW_LOCAL=1`。

**为什么用退出码 2 而不是 1**：脚本约定里 `1` 是"发现了问题"（代码有问题），`2` 是"环境或参数
不满足"。本地跑测试不是代码有问题，是这里不该跑 —— 退出码要能表达这个区别，否则 CI 日志里
两类失败会长得一样。

**例外场景**：正在改测试本身、或排查某个具体用例时用 `TEST_ALLOW_LOCAL=1`，改完不要把它写进
任何脚本。

## 4. 流水线结构

```text
push / PR
   ├── verify   checkout → pnpm install → pnpm verify → pnpm build
   └── test     checkout → pnpm install → pnpm db:migrate → pnpm test → pnpm test:e2e
                 └── postgres:17-alpine service（user/pass/db 都是 test，与 e2e 占位值一致）
   └── ci       汇总闸门：两个 job 都 success 才绿
```

几个刻意的选择：

- **`build` 放在 `verify` job 里**，省一次 `pnpm install`；它不连库，不需要 service
- **`test` job 单独起 Postgres**，而不是让单测连本地库：CI 里的库每次都是干净的，
  "在我机器上能过"这类问题不会出现
- **迁移先于测试**：迁移坏了（SQL 语法、外键顺序、重复索引）应该在跑用例之前就红，
  而不是让测试用一个半成品 schema 报一堆无关错误
- **`ci` 是汇总闸门**：分支保护只勾 `ci` 一项，将来加减 job 不用改仓库设置；
  `if: always()` 保证上游失败时它仍会运行并给出失败结论（否则它会被跳过，PR 显示"待检查"）
- **`--frozen-lockfile`**：lockfile 与 `package.json` 不一致时直接失败，不允许 CI 里悄悄改依赖
- **Node 版本只有一个来源**：`.nvmrc`（22），CI 用 `node-version-file` 读它
- **不引入第三方 action**：只用 `actions/*` 与 `pnpm/action-setup`，少了供应链风险面

## 5. 失败排查顺序

看到红灯先定位是哪一层，不要从头重跑：

0. `install` 就红（连 `pnpm verify` 都没跑到）→ 几乎都是 `ERR_PNPM_IGNORED_BUILDS`，
   见下面「安装阶段的构建脚本裁决」；`--ignore-scripts` 不是解法
1. `verify` 红 → 本地 `pnpm verify` 逐个复现（typecheck / lint / perm:audit 是三条独立命令）
2. `build` 红而 `typecheck` 绿 → 通常是 `nest build` 的 tsconfig（`tsconfig.build.json`）排除了
   某个被引用的文件，看构建日志里的具体文件
3. `db:migrate` 红 → SQL 本身的问题，本地起干净库复现：`docker compose up -d db` 后
   用一个新的库名跑 `DATABASE_URL=... pnpm db:migrate`
4. `test` 红 → 本地 `TEST_ALLOW_LOCAL=1 pnpm test`，只跑相关文件：
   `TEST_ALLOW_LOCAL=1 pnpm test -- src/modules/user`
5. `test:e2e` 红 → 检查 `vitest.config.e2e.ts` 里注入的 `DATABASE_URL` 是否与 service 容器
   的账号/库名一致（当前约定是 `test:test@localhost:5432/test`）

### 安装阶段的构建脚本裁决

pnpm 11 起 `strictDepBuilds` 默认开启：依赖里只要有一个**没裁决过**的安装脚本（`preinstall` /
`install` / `postinstall`），`pnpm install` 就以 `ERR_PNPM_IGNORED_BUILDS` 失败。本地因为
`node_modules` 早就装好了不会触发，CI 是干净安装，所以这个错**通常只在 CI 出现**，看起来像
"代码没改却突然红了"。

处理三步，不要用 `--ignore-scripts` 绕过（它会把 esbuild 的二进制下载也一起跳过，构建会以
另一种方式失败）：

```bash
pnpm ignored-builds     # 只读诊断：Automatically ignored 非空 = 有未裁决的包
```

1. 看清单里的包是谁带进来的：`pnpm why @scarf/scarf`
2. 判断该不该跑：落平台二进制 / 编译原生模块的（`esbuild`、`sharp`、`@parcel/watcher`）→ `true`；
   遥测与统计上报（`@scarf/scarf`）→ `false`
3. 在 `pnpm-workspace.yaml` 的 `allowBuilds` 里写死，随代码提交

**新增依赖后的固定动作**：跑一次 `pnpm ignored-builds`，`Automatically ignored` 必须是 `None`。
这条不是"安全建议"，是 CI 的前置条件 —— 漏了它，PR 会在第一步 `pnpm install` 挂掉。

当前状态：`esbuild: true`（下载平台二进制）、`@scarf/scarf: false`（`swagger-ui-dist` 带进来的
安装期遥测，与本项目功能无关）。

## 6. 一次性配置（仓库设置，不在代码里）

GitHub → Settings → Branches → 保护 `master`：

- Required status checks 勾 **`ci`**（只勾这一个）
- 勾 "Require branches to be up to date before merging"

这两项是网页设置，改不到代码里，换仓库时要重做一遍。

## 7. 已知边界

- **e2e 目前无用例**：`src/__tests__/bootstrap.spec.ts` 走的是 HTTP 全链路但 mock 了
  `DatabaseService`，**不能用来验证 SQL**。真实 SQL 目前只能靠迁移 + curl 验
- **`--passWithNoTests` 会让 e2e 在没用例时静默跳过**：这是有意的过渡态；第一条 e2e 用例
  落地后应当去掉这个参数，让"用例被误删"也能被发现
- **覆盖率不上传**：没有接 Codecov 之类的服务，`pnpm test:cov` 只在需要时本地（带
  `TEST_ALLOW_LOCAL=1`）手动看
